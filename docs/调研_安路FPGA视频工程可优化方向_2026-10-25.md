## 0. 先把账算清楚：瓶颈到底在哪

### 0.1 资源（取自 `td_20261024_185154.log`，TD 自己的 Utilization 表）【实测】

| 项 | 用量 | 占比 | 备注 |
|---|---|---|---|
| `#lut` | 15412 / 19600 | **78.63%** | 其中 `#lut only` 7417/16688 = 44.45%，`#lut&reg` 7995/16688 = 47.91% |
| `#slices` | 8713 / 9800 | **88.91%** | ★ 真正的绑定资源 |
| `#bram`(9K) | 46 / 64 | 71.88% | `#bram9k 46` |
| `#bram32k` | **0 / 16** | **0.00%** | ★ 16 块 32Kb ERAM 一块没用 |
| `#dsp` | 23 / 29 | 79.31% | |
| `#pll` | 3 / 4 | 75.00% | `u_pll0` / `u_pll_sdr` / `u_pll_aud` |

**一个被忽略的关键事实**：`#slices 8713` 但 `#lut 15412`。EG4S20 的 slice 是「2×LUT4 + 2×FF」结构（9800 slice × 2 = 19600 LUT，正好对上手册的 19600 LUT4 / 19600 FF）。若 15412 个 LUT 两两配对进 slice，理论只需 **7706 个 slice（78.6%）**，实际用了 8713 —— **约 1007 个 slice（≈10 个百分点）是被"配对失败/布局分散"浪费掉的**，不是逻辑真的那么多。这决定了方向 1 里"省面积"的正确打法：**不是单纯删逻辑，而是让 LUT 和 FF 成对落地**。

### 0.2 时序（同一次 build）【实测】

```
Setup : WNS -6692ps  TNS -420020ps  NUM_FEPS 246
Hold  : WNS     4ps  TNS       0ps  NUM_FEPS   0
```

- 246 个端点一起吃 Setup 违例、TNS -420ns，**平均每条违例 1.7ns** —— 这不是"某一条长路径"，而是**一整组时钟关系的系统性违例**，正好对上你说的 125MHz 0°/180° 那一组（`u_pll_sdr/pll_inst.clkc[1]` 与 `clkc[2]`，见 `m2.sdc` 第 18/22 行注释）。
- 物理综合在拼命救它，但救不动【实测】：
  ```
  OPT-0007 : Iter 1: improved SWNS -6843 STNS -294560 NUM_FEPS 80 with 37 cells processed and 1050 slack improved
  PHY-1001 : Iter 1; Processed 93 pins with SWNS -6.692ns STNS -338.089ns FEP 155
  ```
  迭代只把 −6843ps 挤到 −6692ps（救了 151ps），处理了 93 个 pin 仍然 −6.692ns。
- **Hold 其实是过的**（+4ps）。你记的 −12ps / 4 端点应该来自另一次 build（`ab_baseline_rebuild.log` 里是 `Hold WNS -0.020ns FEP 2`）。这一条优先级应当**下调**：12~20ps 的 hold 违例在 55nm 器件上属于 OCV/时钟不确定性噪声量级，且只有 2~4 个端点。
- 拥塞是真实存在的【实测】：`PHY-1001 : Congestion: {69.27, 63.89, 61.07, 59.16}`，`Congestion index: top1 = 111.57 (S 180.78, N 185.09, E 106.96, W 137.76)` —— **南/北方向（S/N）热点明显高于东（E 106.96）**，说明拥塞是**局部**的，不是全局均匀。

### 0.3 带宽（全是【推算】，但结论很硬）

| 通路 | 数据量 | 耗时 |
|---|---|---|
| SDRAM 峰值带宽 | 2M×32bit @125MHz | **500 MB/s**（手册给合封 SDRAM 上限 200MHz/800MB/s） |
| 显示读 SDRAM | 480000 px/帧 ÷ 2px/字 = 240000 字/帧 × 60Hz | 14.4M 字/s = **57.6 MB/s（占 11.5%）** |
| 装载写 SDRAM（一张图） | 240000 字 @125MHz | **1.92 ms** |
| SD 卡 SPI（现状 25MHz） | 3.125 MB/s 有效 | 一张 1536×1152 BMP 抽行后约 2.65MB → **848 ms** |

**结论：SDRAM 完全不是瓶颈（写一张图 1.9ms vs SD 读 850ms，差 440 倍）。换图的 1~2s 有 99% 花在 SD 卡上。** 方向 2 的"带宽优化"对本工程基本无收益，真正该做的是方向 3 + 后台预取。

## 1. TD 6.2 综合/布局布线：资源与时序优化

### 常见做法（手册口径）

TD 综合分三段：**Read Design → Optimize RTL → Optimize Gate**（`Process → Properties` 或右键 `Syn Opt → Properties`）。可调项与取舍【手册，见 [SWUG106 精讲](https://liazun.com/%E7%A7%BB%E8%BF%9Cfpga%E7%AB%9E%E8%B5%9B%E5%AE%89%E8%B7%AF/hdl%E7%BC%96%E7%A0%81%E4%B8%8E%E7%BB%BC%E5%90%88/)】：

- **Read Design**：`infer_add`（≥`min_ripple_len` 走进位链）、`infer_mult`、`infer_ram/rom`、`infer_fsm(OFF/ONEHOT/AUTO)`、`infer_shifter`
- **Optimize RTL**：`max_fanout`（默认 9999，超阈值自动复制寄存器降扇出 = 你问的 *register duplication*）、`keep_hierarchy(FLATTEN/AUTO/MANUAL/ALL)`、`opt_mux`/`merge_mux`、`gate_sharing`、`resource_sharing`
- **Optimize Gate**：`opt_area(HIGH/MEDIUM/LOW)`、`opt_timing`、`map_strategy(1 均衡 / 2 用更大 LUT 压组合级数)`、`pack_effort(HIGH/MEDIUM/LOW)`、`pack_seq_in_io`
- **HDL attribute**：`allow_forward_retiming` / `allow_backward_retiming`（retiming）、`max_fanout`、`dsp_style`、`ram_style(bram_9k/_20k/_32k + fast/power/area)`、`shifter_style`、`fsm_encoding`、`resource_sharing`、`keep`、`keep_hierarchy`、`clock_buffer(gclk/sclk/lclk/mclk/none)`
- **retiming 官方态度**：功能不变、把逻辑从紧张侧挪到松弛侧；但**改变网表结构、前后网表难对应、运行时间更长，"应尽量少用"**。
- **时序估算尺**：PH2A 器件每级组合 ≈ 500ps，1 级 ≈ 1 个 6 输入 LUT；32bit 加法（进位链）2 级；27×18 乘法（DSP，带 outreg）2 级；**带 outreg 的 ERAM 0.5 级，不带 outreg 的 2 级**（这条直接说明：RAM 一定要开输出寄存器）。
- **面积条目（原文）**：去掉多余 `keep`；慎用 `keep_hierarchy`（会阻止跨模块常数传播与合并）；**统一同步复位**（异步复位必须占 DFF 的控制逻辑，同步复位可被 LUT 吸收；同步/异步混用会导致两个寄存器无法相邻摆放）；常数乘法换移位加（`a*9=(a<<3)+a`）；资源共享（`sel?a*b:c*d` → `(sel?a:c)*(sel?b:d)`）。

### 对本工程是否适用

适用，但要**按收益排序**，且有一条硬约束必须尊重：

> ⚠️ **你的 `m2.sdc` 里已经用血的教训写过**（第 64–79 行）：多声明一组 `set_clock_groups` 会改变全局布局，进而让 SDRAM 核"用 180° 采 DQ"那条路失效，实测 **2048 个字里错 1536 个**。
> ⇒ **本工程任何影响布局的改动（加例外、改综合选项、改利用率），都必须重跑"读回逐字比对"自测再上板。**

1. **[P0] 先把 246 个失败端点归因**，再决定是"加例外"还是"降频"。
   - 用 TD 的 Timing 工具出报告（命令与五类报告见 [SWUG201 时序工具精讲](https://liazun.com/%E7%A7%BB%E8%BF%9Cfpga%E7%AB%9E%E8%B5%9B%E5%AE%89%E8%B7%AF/%E6%97%B6%E5%BA%8F%E5%B7%A5%E5%85%B7/)），看这 246 条的 start/end 是不是都落在加密核 `b_display/lib/sdram/*.enc.v` 里。
   - 若都在核内：这是 IP 的已知结构，**加"定向"例外**（只在具体寄存器上，不动时钟组）：
     ```tcl
     # 只对具体端点，不写 set_clock_groups —— 避免重演 2026-09-27 那次事故
     set_false_path -from [get_regs {u_sdram/*}] -to [get_regs {u_sdram/*}]
     # 或若确认是"两拍才采一次"的结构：
     set_multicycle_path 2 -setup -from [get_clocks {u_pll_sdr/pll_inst.clkc[1]}] \
                                 -to   [get_clocks {u_pll_sdr/pll_inst.clkc[2]}]
     ```
     语法与四种多周期场景（含**固定相位差同频时钟**这一种）见 [SWUG200 时序约束精讲 tcons-02](https://liazun.com/%E7%A7%BB%E8%BF%9Cfpga%E7%AB%9E%E8%B5%9B%E5%AE%89%E8%B7%AF/%E6%97%B6%E5%BA%8F%E7%BA%A6%E6%9D%9F/tcons-02)。手册明确写了加 false path 的收益是"**减少分析时间、提高结果质量（QOR）：工具不再在伪路径上浪费修复精力而冷落真正的功能路径**"——这正好对应你现在 `Iter 1: 93 pins ... SWNS -6.692ns` 的无效迭代。
   - 若不在核内：那是你自己 125MHz 域的真路径，别加例外，往下看第 3 条。

2. **[P0] 备选：把 SDRAM 域从 125MHz 降到 100MHz。**
   - 现约束是 `u_pll_sdr` 的 `clkc[1] = multiply_by 2.5`、`clkc[2] = multiply_by 2.5 -phase 180`【实测，日志 `USR-1002 : Derived clock`】。2.5 倍是"半整数倍频"，对 PLL 的占空比与相位精度要求最高的一档；改成 `×2.0`（100MHz）是整数倍频，最稳。
   - 带宽代价：500→400MB/s，而你只需要 57.6MB/s（11.5%）→ **毫无影响**。
   - 收益：−6.692ns 的 246 个端点随频率下降直接消失（8ns 周期里 6.7ns 的亏空，在 10ns 周期里就是 -4.7ns —— 仍不够，所以这条只能配合第 1 条一起用；真正作用是**把"半整数倍频+180°相位"这条最脆的关系简化掉**）。
   - 风险：SDRAM 核的时钟树敏感（同上），必须重跑读回自测。

3. **省 slice 的正确打法：让 LUT 与 FF 成对落地。**
   - 现状 `#lut&reg 7995` / `#lut only 7417`，而 slice 用了 8713 个 → 约 1007 个 slice 浪费在配对失败。
   - 手段：① 模块出口统一打拍（组合输出后面跟一个 FF，综合器才愿意把它俩塞进同一 slice）；② `pack_effort=HIGH`；③ `opt_area=HIGH`（手册警告 HIGH 可能伤时序，你现在时序本来就紧，**先只对非 125MHz 域试**）；④ `max_fanout` 压到 64~128 让工具自动复制寄存器降扇出（你 88.9% 的 slice 占用下，扇出过大的网更容易被拉成长线）。

4. **统一同步复位。** 你工程里 `soft_rst`、`arst`（日志有 `td_20261021_arst*.log` 一串实验）混用。手册原文：**混用同步/异步复位会导致两级寄存器无法相邻摆放**。改成全同步复位能直接省 slice，且能改善 hold（同步复位的复位端可被 LUT 吸收）。

5. **`keep_hierarchy` 该 FLATTEN 了。** 你 `top_m2.v` 已经把 20+ 模块平铺在一个文件里，还有大量调试探针（`B_DEBUG_PROBE` 宏）。跨模块常数传播一旦被 `keep_hierarchy=MANUAL/ALL` 挡住，MUX 与比较器就消不掉。改成 `FLATTEN` 通常能省 3~8% LUT。

6. **hold fix 被跳过的规避。** 手册没有直接讲"利用率 >90% 跳过 hold 修复"的阈值，但机制清楚：hold 修复要靠插延迟单元/改布局，**布局已无空位时工具只能放弃**。所以正确顺序是：**先把 slice 压到 85% 以下，再重跑**。对仅剩的 2~4 个 −12~−20ps 端点，最省事的办法是手工路径加 1 级 LUT（约 0.5ns，足够覆盖 20ps）或 `set_min_delay`，**不要为它改全局约束**。

7. **retiming：可以试，但别指望。** 你 125MHz 域的问题是"结构性的时钟关系"，不是"组合级数多了 1 级"。retiming 更适合 40MHz 像素域里那些 `v_cnt→scaler` 的长组合链（手册说每级 500ps，40MHz 有 25ns，塞 10 级都够——所以像素域本来就不该违例，违例说明是被拥塞拖的）。

### 预期收益 / 风险

| 措施 | 收益 | 风险 |
|---|---|---|
| 246 端点定向例外 | TNS -420ns → 0；布线器不再无效迭代，QoR 可能连带改善 | 例外写错 = 真违例被藏起来；**必须上板跑读回自测** |
| SDRAM 125→100MHz | 时序组整体松 2ns | 带宽降 20%（无所谓）；时钟树变化敏感 |

## 2. SDRAM 外部存储带宽优化

### 常见做法

- **Bank 交错（interleaving）**：把连续地址轮流映射到 4 个 bank，一个 bank 在 precharge/激活时另几个还能传数据，消除"换行惩罚"。Intel 的白皮书就是讲这个：[Using Interleaving to Increase Bandwidth](https://www.intel.com/programmable/technical-pdfs/683106.pdf)。
- **突发长度**：SDRAM 的 BL=2/4/8 + 顺序/交错模式；BL 越长，命令开销占比越低。
- **双/多缓冲**：读写不同帧缓冲，避免"读着旧帧写新帧"的撕裂。
- **写回策略**：write-back（先在片内攒够一行再突发写）vs write-through。
- **读写冲突**：SDRAM 单端口，读→写切换要付 tRTW/tWTR 惩罚；高优先级请求会饿死另一方。
- **读门控**：不需要读时彻底关掉读请求，别让仲裁器空转。

### 对本工程是否适用

**"带宽"这一半不适用，已经过剩 8.7 倍；"访问模式"这一半很适用。**

1. **别再优化带宽。** 需要 57.6MB/s，有 500MB/s。写一张图只要 1.92ms。方向 2 的所有"提带宽"手段（bank 交错、加突发长度）收益 ≈ 0 —— 因为带宽不是瓶颈，**而且核是加密的（`sdr_as_ram.enc.v` / `sdr_wrrd.enc.v`），你改不了它的突发长度与 bank 策略**。

2. **能改的是"地址局部性"。** 你注释里写了"sdr 核是 4 字一包（16B = 8 个 RGB565 像素），读写都认"【实测】。保证每次请求都是**连续 4 字对齐的整包**，就能吃满突发；行缓冲按"一整行 400 字连续读"就是这个思路（`line_buf.v` 注释：一行 400 字 @125MHz ≈ 3.2~6.4µs，占一行显示时间 26.4µs 的 1/8~1/4）。

3. **多缓冲已经做了，要把它用起来。** `artwork_def.v` 里有**两个大槽**：`SLOT0_BASE=0 / SLOT0_WORDS=930832`（前台）、`SLOT1_BASE=930832 / SLOT1_WORDS=930828`（后台，转场用）【实测】。现在的用法是"切图时才装载 → 白屏 → 转场"，**它本来就该是"显示 A 的同时往 B 装"**。这是第 7 节 P0 的基础。

4. **把字幕从 SDRAM 搬进空着的 ERAM。** `#bram32k 0/16`，**16 块 32Kb ERAM 一块没用**；而字幕是 10 条 × 800×64 1bpp = 512,000 bit，**16 × 32Kb = 512Kb ≈ 512,000 bit，几乎精确相等**【实测+推算】。搬过去的好处：① 每帧少读 1600 字；② 腾出 `SDR_SUBTITLE` 的 16,000 字；③ 字幕读延迟从 SDRAM 的几十 ns 变成单拍。

5. **读写冲突的真实场景**：装载期显示读 57.6MB/s + 写突发，两者抢同一个口。你已经有 `transition.v` 的 `PASS + white_a`（整屏白）来"把 SDRAM 读口静音"——**这是本工程最聪明的一处设计**，别改掉。若要进一步：把写口优先级设成"只在行消隐期突发写"（一行 20µs 里有 5.6µs 消隐）。

6. **要不要上 APUG011（ERAM 接口，200MHz/800MB/s）？** 不建议。收益为 0（带宽过剩），代价是重做整个 SDRAM 集成 + 重跑读回自测 + 大概率破坏现在已调好的 180° 采样关系。

### 预期收益 / 风险

| 措施 | 收益 | 风险 |
|---|---|---|
| 地址整包对齐（4 字连续） | 消除零碎请求，行缓冲更稳 | 无 |
| 字幕搬 ERAM | 每帧省 1600 字读；腾 16k 字 SDRAM | 需处理 ERAM 上电无初值（见方向 5） |
| 用起双槽做后台装载 | **感知装载时间 1~2s → 0** | 见第 7 节 |
| 上 APUG011 | ≈0 | 高，不值 |

## 3. SD 卡读取吞吐

### 常见做法

- **SPI 模式 vs 4-bit SD 模式**：SPI 是 1 根数据线、协议简单、上限低；SD 模式是 4 根数据线并行 + CMD18 多块读，理论 4 倍带宽。
- **CMD18（READ_MULTIPLE_BLOCK）**：一次命令连续读多个块，块间不需要重新发命令、不需要撤 CS，最后用 **CMD12（STOP_TRANSMISSION）** 收尾。定义见 [SD 物理层简化规范 v9.00](https://www.sdcard.org/cms/wp-content/themes/sdcard-org/dl.php?f=Part1_Physical_Layer_Simplified_Specification_Ver9.00.pdf)。
- **时钟提速**：SPI 模式规范上限 25MHz（default speed）；50MHz 属超规格但多数卡能吃。
- **DMA/预取**：把"读"和"用"解耦，读的时候 CPU/状态机干别的。
- **簇大小**：FAT32 每簇 4KB~32KB，簇越大 FAT 链越短、寻址次数越少。

### 对本工程是否适用

**先说硬约束（这条能省掉你半天纠结）：4-bit SD 模式在这块板子上物理不可行。**
`m2_pin.adc` 里 SD 只连了 4 根：`sd_ncs=A12 / sd_dclk=A14 / sd_mosi=A13 / sd_miso=B14`，**没有 DAT1/DAT2/DAT3/CLK 的管脚**，全是 LVCMOS33【实测】。所以只能走 SPI。

**现状（比你以为的好）**【实测】：
- 初始化阶段 `sd_init` 用 `sck_div=35` @50MHz → SCLK = 50/(4×36) = **347kHz**，符合规范的 ≤400kHz 初始化要求；
- 数据阶段 `sd_read_cdc` 把**整个 `sd_read`（含 `my_spi`）搬到 100MHz**、`sck_div=0` → SCLK = 100/4 = **25MHz**，**已经是 SPI 模式的上限**。

**所以"时钟提速"这一项只剩两条路**：① 25→50MHz（超规格，靠卡兼容性）；② 换协议（不可行）。

**真正的大头是"每块的固定开销"。** 你自己在 `sd_read.v` 注释里量化过：每块 CMD17 要多付 **~120µs** 的卡访问延迟（撤 CS → CMD17 → 卡内部访问 → token）【实测】。算一下：

```
25MHz SPI：一个 512B 扇区有效传输 = 512×8/25MHz = 164µs
加 120µs 固定开销 → 284µs/扇区 → 有效吞吐只剩 1.80MB/s（带宽利用率 58%）
```

**把一张图的账走完（以卡上 1536 宽的图为例，`bmp_analyze.v` 注释说卡上有 640/800/1080/1536 四种宽度，>900 行时按 ÷2 抽行）**【推算】：

| 阶段 | 字节 | 25MHz 纯传输 | +120µs/扇区 | 说明 |
|---|---|---|---|---|
| 现状：抽行后仍整行读（不跳列） | 576 行 × 4608B = 2.65MB | 848ms | **+622ms ≈ 1.47s** | ✅ 与你"1~2s"吻合 |
| 只上 CMD18 | 同上 | 848ms | +0（块间无缝） | **1.73×**（你仿真测到 1.32×，说明仿真的块开销设小了） |
| CMD18 + 跳列（真读 768 列） | 576×768×3 = 1.33MB | 425ms | 0 | **3.5×** |
| 再换 RGB565 素材（2B/px） | 884KB | 283ms | 0 | **5.2×** |
| 再降素材到 640×480 RGB565 | 614KB | 197ms | 0 | **7.5×** |

**具体建议（按性价比）**：

1. **[P0-必做] 修好 CMD18。** 你已经写了（`CMD18=8'h52`、`CMD12=8'h4C`、`stream_en`、`my_spi` 还专门加了 `spi_clk_en` 冻结时钟），仿真 1.32×、逐字节一致，但上板"随后的音频/字幕装载全部 fail=1"。两个待办你自己也写了：
   - **CMD12 之后必须等 busy 释放**（数据线被卡拉低），再发下一条命令 —— 这是"后续全部失败"的最典型原因：上一条多块读没真正停止，后面所有命令都撞在数据传输中间。
   - 校验 `R1b` 响应 + 超时重试；对不认 CMD18 的卡做**运行时降级**（先试 CMD18，失败则永久回 CMD17）。
2. **[P0-必做] 素材侧改造，零 RTL 成本。**
   - 存 **RGB565 原始二进制**（无 BMP 头、无行补齐）→ 字节数 −33%，而且省掉 BMP 头解析与 24→16bit 转换逻辑（那部分也是 LUT）。
   - 直接把素材做到 **640×480 或 768×576**，显示端用你已有的 `bilinear.v` 放大 → 再省 44~64%。
   - 这两个改动合起来让装载降到 ~200ms 量级。
3. **[P1] 跳列。** 现在只跳行。BMP 未压缩，跳列必须"半路撤 CS + 重新 CMD17 到本行下一个要用的地址"，能再省 50% 字节。实现复杂度中等，收益大（尤其宽图）。
4. **[P1] 簇大小 32KB。** FAT32 下 4KB 簇 = 每 64 个扇区就要读一次 FAT；32KB 簇 = 每 64 个扇区一次 FAT（比例不变但**单次寻道距离更短、顺序性更好**），实测通常能省 3~8% 时间。更省事的做法：把一个文件**连续存放**（碎片整理），这样连 FAT 都不用跟。
5. **[P2] 50MHz SPI。** 超规格。SD 规范只保证 25MHz；多数卡能跑 50MHz，但**上板会随卡型号翻车**。建议：做成参数（`sck_div` 从 0 改不了，得改 `sd_read_cdc` 的分频），比赛现场用 25MHz，平时试 50MHz。
6. **[P0-最有效] 后台预取**（见第 7 节）：装载时间从"用户看得见"变成"看不见"，比任何提速都值。

### 预期收益 / 风险

| 措施 | 收益 | 风险 |
|---|---|---|
| CMD18 修好 | 1.7×（848+622ms → 848ms 或更低） | 卡兼容性；CMD12 时序写错会连环失败 |
| RGB565 + 降素材尺寸 | 再 3× | 画质（靠 bilinear 放大弥补）；要重做素材 |
| 跳列 | 再 2× | 需要在行内多次撤/起 CS，状态机复杂度上升 |
| 簇 32KB / 连续存放 | 3~8% | 无 |
| 50MHz SPI | 2× | 超规格，现场翻车风险 |

## 4. 视频缩放与转场画质

### 常见做法

- **最近邻**：1 个像素搞定，零 DSP，但缩小严重混叠、放大成马赛克。
- **双线性**：横向 2 抽头 + 纵向 2 抽头，可分离 → 每像素 3 次插值（不是 4 次）。
- **多相（polyphase）**：把缩放比分解成 N 相，每相预存一组系数，适合非整数倍缩放的抗混叠（Xilinx VPSS 的 5×5 / 6×6 缩放网格就是这么做的，见 [PG231](https://www.xilinx.com/content/dam/xilinx/support/documents/ip_documentation/v_proc_ss/v2_4/pg231-v-proc-ss.pdf)）。
- **Alpha 混合**：`out = A + (B−A)·α`，α 用 8bit。
- **双缓冲防撕裂**：在 VSYNC 边界整体切缓冲。

### 对本工程是否适用

**你已经做了双线性（`bilinear.v`），所以这一节的收益不在"有没有"，而在"缩小档"和"乘法器数量"。**

现状【实测，`bilinear.v` 头部】：
- 可分离两遍插值：`top=p00+fu(p01−p00)` / `bot=p10+fu(p11−p10)` / `out=top+fv(bot−top)`，权重 `fu/fv ∈[0,255]`、除以 256（`>>8`）；
- 先把 RGB565 展开成每通道 8bit 再插值，最后截回 565（**这点做对了**，直接对打包 565 做加减会通道串位）；
- **每通道 3 次插值 × 3 通道 = 9 个小乘法器**，注释自己写了"设计说明里低估成 3 个"。这 9 个乘法器基本就是你 29 个 DSP 里的 9 个。

**两个可优化点：**

1. **[P1] 缩小档的"权重=0 退化成抽点"是画质硬伤。**
   `bilinear.v` 注释写"缩小档权重 = 0 退化成抽点"。缩小 2 倍时抽点 = 每 2×2 块只取 1 个像素，**丢掉 3/4 的能量** → 细节密集的图会闪、摩尔纹、边缘爬行。
   改法（按成本）：
   - **盒式平均**：`step ≥ 2` 时对 2×2（或 4×4）做平均 = 3 次加法 + 2 次右移，**0 个 DSP**，画质比最近邻好一大截；
   - 半像素偏移：抽点时取 `(x+0.5)*step` 而不是 `x*step`，能消除"整幅图偏移半像素"的系统性误差。
2. **[P1] 9 个乘法器 → 1 个，时复用。**
   像素率 40MHz（25ns/像素），一个 18×18 DSP 能跑 350MHz（手册：乘法器最高 350MHz，可拆 9×9）→ 25ns 内跑 9 次 8×8 乘加绰绰有余。改成"1 个 DSP + 9 拍状态机"，**省 8 个 DSP（23→15，79%→52%）**，代价是像素流水线加 1 行延迟（有 `line_buf` 兜着，无所谓）。
   > 这也顺带解决了 DSP 79% 的高占用——你现在的 DSP 里有 9 个是这一个模块吃掉的。

3. **[P2] 多相系数表**：如果缩放比固定（比如永远 1536→800，比例 0.5208），可以预存 32 相 × 4 抽头系数到 ERAM/BRAM，把"乘法+加法"变成"查表+乘加"，抗混叠更好。但你现在已经有 2×2 盒式 + 双线性，权衡不值——**除非评委会盯着缩放质量看**。

4. **转场/防撕裂你已经有 `transition.v`（PASS/WIPE/BLIND/XFADE）和双槽**，这块不用改。唯一建议：XFADE 时 `out = A + (B−A)·prog/256` 是每通道 1 次乘 → 3 个乘法器；可以复用第 2 条的时复用乘法器。

### 预期收益 / 风险

| 措施 | 收益 | 风险 |
|---|---|---|
| 缩小档盒式平均 | 缩小画质显著提升（无混叠） | 少量加法器；要改 `win_sample`/`scaler_addr` |
| 乘法器时复用 | DSP 23→15（−28%） | 像素流水线加延迟；时序要重新验 |
| 多相系数表 | 非整数倍缩放更干净 | 收益/成本比低，不建议 |

## 5. OSD 字幕/菜单/可视化渲染

### 常见做法

- 点阵字模放 BRAM/ROM，按 (字符码, 行) 查表；
- 1bpp 掩码（最省）→ 2/4bpp alpha（抗锯齿）；
- 按行缓存字幕，只在该行显示时读；
- 字体压缩：RLE、按字符子集裁剪、按 4bit/像素。

### 对本工程是否适用

**你踩过一个非常关键的坑，而且判断是对的，值得写进报告：**

`font_rom.v` 头部【实测】：
> 「本模块**一定不会落 BRAM**（这版 EG4S20 的 BRAM **不能上电初始化**）：本模块没有任何数组/寄存器（没有 `reg [6:0] mem[0:63]` 那种被综合器认成"块 RAM"的写法），只有一条**纯组合 `case` 常量赋值**；综合器对这种"常数 case"只会落 **LUT**……面积：约 56 个码 × 7 行 → 一张 7 位输出的小查找表，几十个 LUT 而已（实测远小于 +400 LUT 的预算）。」

这段判断在"用 LUT 实现 ROM"这一点上完全正确。量化一下：5×7 点阵 × 56 码 = 1960 bit；LUT4 当 16bit ROM 用 → 理论下界 1960/16 = **123 个 LUT4**，加多级 MUX 实际 **150~250 个 LUT4**（占 19600 的 0.8~1.3%）。**现在这个量级不值得动。**

**但如果要加中文/更多字形，绝对不能走 LUT 这条路**：16×16 汉字 = 256 bit/字，2048 字 = 512Kbit —— LUT 实现要 3 万个 LUT，直接爆。

**推荐做法（绕开"BRAM 不能上电初始化"）**：
1. **开机从 SD 卡把字库读进 ERAM**（`#bram32k 0/16` 全空着！16×32Kb = 512Kb = 正好 2048 个 16×16 汉字）。上电时读一次（512Kb @25MHz SPI = 164ms，用户无感），之后就是片内 ROM。这样既不用初值，也不吃 LUT。
2. 同理，**字幕遮罩也可以搬进 ERAM**（10 条 × 800×64 1bpp = 512Kbit，正好又是 16 块 32Kb）。
3. 若 ERAM 要当 ROM 用，务必开**输出寄存器**（手册：带 outreg 的 ERAM 0.5 级 ≈ 250ps，不带 outreg 的 2 级 ≈ 1ns，差 4 倍）。

**其他可优化点：**

4. **[P2] 字幕现在是 SDRAM 里的 1bpp 掩码**（`SDR_SUBTITLE_STRIDE = 1600` 字/条，800×64）【实测】。优点：省 BRAM；缺点：每帧要读 1600 字（占显示带宽 0.7%），且延迟高。搬到 ERAM 后延迟 <5ns。
5. **[P2] 抗锯齿**：5×7 点阵放大 2 倍（`TXT_SCALE=2` → 10×14）时边缘是台阶。做 4bpp alpha 需要 4 倍存储（800×64×4bit = 20,480 字/条 × 10 条 = 太大）。折中：**只对字幕做 2bpp**（每个像素 2bit，4 级灰度），存储翻倍但可接受，视觉上边缘柔和很多。代价：混合要 1 次乘加（可用移位近似：2bpp = α∈{0,1/3,2/3,1} → 用 `(a+2b)/3` 之类，免乘法）。
6. **[P2] 菜单半透明**：现在 `menu_ovl` 是**不透明底板**（"绝不透出照片"）。若要半透明，需要每像素 1 次乘加 × 3 通道 = 3 个乘法器（或时复用）。建议只对**菜单边框/高亮条**做半透明，底板保持不透明——省 DSP 且视觉上足够。
7. **【范例】可视化条的省资源做法你已经是教科书级了**：`viz_freq.v` v2 是"24 级并行"（Vivado 实测 3068 LUT/1537 FF ≈ 安路 1050 MSlice，上板出不来），v3 改成**时间复用**（一个共享运算单元，每个采样打 N 拍；48kHz 采样、clk_aud 12.288MHz → **每个采样 256 拍**，扫 24 拍绰绰有余），预测 ~400 LUT / ~1050 FF，**省 2600 LUT**【实测，模块头注释】。这条经验可以直接套到别的地方（见第 7 节）。

| 措施 | 收益 | 风险 |
|---|---|---|
| 字库/字幕进 ERAM | 省 LUT、省 SDRAM 带宽、延迟降到 ns 级 | 上电要装载 164ms；32Kb 块是 16 位宽，注意拼接 |
| 2bpp 字幕抗锯齿 | 观感提升 | 存储×2，混合逻辑略增 |

## 6. 音频链路

### 现状（从 RTL/日志读出来的，比问题描述更精确）

- **音频不走外部 DAC，走 HDMI 数据岛**：`lib/audio/` 下有 `hdmi_audio_tone_i2s_64fs.v`、`I2S_receiver.v`、`i2s_rom_player_single_pll_fix64_rom_ip.v`【实测】。
- **音频时钟是 HDMI PLL 派生，不是 12.288MHz**：`top_m2.v` 第 1106–1130 行注释【实测】：
  > 「音频 PLL（A 轨的音频链要 12.288 MHz）……用原厂例程里现成的 `PLL_HDMI_AUDIO`：C0=75M / C1=375M / C2=**12.295082M**。C2 比 12.288 高 **+576 ppm** —— 音调高 0.058%，人耳听不出来」
  TD 日志也确认：`u_pll_aud/pll_inst.clkc[2]` = `divide_by 4.0667`（50/4.0667 = 12.295MHz）。
- SDRAM 音频区：`SDR_AUDIO_WORDS = 120000` 字 = 240,000 采样 = **5 秒 @48kHz 单声道 16bit**；卡上 `mus0.wav` 3.61s = 86,657 字、`mus1.wav` 2.07s = 49,639 字【实测】。

**由此推出一个必须处理的真问题**：实际采样率 = 12.295082MHz / 256 = **48.0277kHz**，比标称 48k 快 0.058%（无所谓）；但**如果卡上是 44.1kHz 的 WAV，直接播会快 8.84%（接近一个半音），明显跑调**。

### 常见做法

- **I2S 三线**：SCLK（位时钟，= 64×Fs 或 32×Fs）、WS/LRCK（左右声道选择，= Fs）、SD（数据，MSB 先、相对 WS 沿延迟 1 bit）。
- **采样率不一致**：① 离线重采样（最省）；② 在线线性插值重采样（相位累加器 + 1 个乘法器）；③ 丢/复采样（音质差）。
- **音量插值防爆音**：音量变化时不能一步跳变，要在 10~20ms 内线性斜坡（48kHz 下 480~960 个采样）。
- **省资源的频谱**：不用 FFT，用**滤波器组**（一阶低通串联，相邻两级输出相减 = 该频带能量），纯移位加法，0 DSP。

### 对本工程是否适用

1. **[P0，零成本] 素材统一成 48kHz。** 用 `ffmpeg -i in.wav -ar 48000 -ac 1 -sample_fmt s16 out.wav` 或 `sox in.wav -r 48000 out.wav` 离线转换。RTL 一行不用改，跑调问题消失。同时**统一成单声道 16bit**（SDRAM 音频区就是按这个算的）。
   - 注意 44.1k→48k 的重采样上线要加**抗混叠低通**（ffmpeg/sox 默认会加），否则高频会折叠。
2. **[P1] 音量斜坡。** 你换歌/静音时若直接改系数，会有"咔"声。做法：目标音量 `vol_tgt`、当前音量 `vol_cur`，每采样 `vol_cur += 1`（或每 N 采样加 1）直到相等 → 480 个采样 = 10ms 斜坡，**0 乘法器**（因为 `>>k` 分级衰减本来就是移位）。
3. **[P1] 音效与音乐混音要饱和。** `sfx_player` + 音乐两路相加，16bit + 16bit 会溢出 → 必须做饱和（`if (sum > 32767) 32767`），否则大音量时爆音。这是"沙沙声/破音"的经典来源（你 `artwork_def.v` 注释里记录的"一片沙沙"是地址重叠，但混音溢出会是另一种爆音）。
4. **[已完成，可再省] 可视化不是 FFT 而是滤波器组**（`viz_freq.v`：N 级一阶低通串联，`band_k = |y[k−1] − y[k]|`，`α = 2^-a+2^-b+2^-c` 纯移位，**零乘法零除法零 DSP**；对数刻度用"找最高位 + 取下面 3 位小数"近似 log2，约 1.9dB 一级）。这条路已经比 24 点 FFT 省 2600 LUT。可再省：24 段 → 16 段、柱高量化到 8 级（对数刻度本来就是粗的）。
5. **[P2] 若要支持长音频**：5 秒缓冲不够放完整歌曲，现在靠"随图切换重装"。可以扩 `SDR_AUDIO_WORDS`（SDRAM 末尾还剩 31,300 字），或做双音频区（A 播 B 装）。注意与图像预取抢 SPI 带宽（一首 3.6s WAV = 346KB = 111ms @25MHz，比图的 850ms 小得多）。
6. **12.295MHz 的 +576ppm 要不要修？** 不要。HDMI 的音频时钟必须和 TMDS 像素时钟同源（音频 N/CTS 关系），改成精确 12.288MHz 反而会让 HDMI 接收端重采样/静音。0.058% 的音高偏差人耳阈值约 0.5%（5 音分），差一个数量级。

### 预期收益 / 风险

| 措施 | 收益 | 风险 |
|---|---|---|
| 素材统一 48k 单声道 | 跑调消失，零 RTL | 无 |
| 音量斜坡 | 换歌/静音无爆音 | 无 |
| 混音饱和 | 消除大音量破音 | 无 |
| 可视化降段数 | 再省 ~100 LUT | 观感略糙 |
| 双音频区 | 换歌不中断 | 占 SDRAM；与图像预取抢 SPI |

## 7. 优先级建议（先做什么、为什么、大概多少收益）

### P0-1　把"换图装载"从"切图时"挪到"显示中"（后台预取 + 双槽）★最高性价比

- **为什么**：你已经有两个大槽（`SLOT0` 前台 / `SLOT1` 后台，`artwork_def.v` 第 231–234 行），**硬件结构天生支持**"显示 A 的同时往 B 装"。现在却是切图 → 全白 → 装 → 转场，把 850ms 的 SD 读取直接暴露给观众。
- **怎么做**：6 秒展示期里的前 1.5 秒，让 A 轨装载机往**后台槽**写下一张；写完后 `desc_tx` 更新描述符的 `valid`，转场时直接切。`transition.v` 的 `PASS + white_a` 白屏只保留 1 帧（用作"装载期的读口静音"），而不是 1.5 秒。
- **收益**：**感知装载时间 1~2s → ≈0**。这是唯一能把"停顿"彻底消掉的改动，且不依赖任何提速。
- **风险**：装载与显示争 SDRAM 口（实测带宽只用 11.5%，够）；`desc_rx` 的帧边界采样逻辑要改（描述符表在片内，需双缓冲）；音频区只有 5s，换歌也要预取（111ms，好办）。

### P0-2　诊断 246 个失败端点 → 定向例外或降频

- **为什么**：TNS −420ns / 246 端点，布线器每轮迭代都在救一条救不动的路（`93 pins ... SWNS -6.692ns` 反复出现），既浪费时间又**改变布局、加剧拥塞**（你自己的注释写过"工具为了满足不可能收敛的跨域路径，把布局挤到 85% 以上，反而把真路径拖成违例"）。
- **怎么做**：先 `report_timing` 看这 246 条的 start/end 是否都在 `u_sdram/*` 里；是 → 只对这些寄存器写 `set_false_path`（**不要动 `set_clock_groups`**，你在 `m2.sdc` 第 64–79 行有 1536/2048 字错的血泪史）；不是 → 那是真路径，考虑 SDRAM 域 125→100MHz。
- **收益**：TNS 归零、拥塞下降，可能换来 slices 2~5 个百分点的改善（间接）。
- **风险**：例外写错会藏真违例 → **每次改完必须跑读回逐字比对再上板**。

### P0-3　素材侧改造（RGB565 + 降到 640×480/768×576）

- **为什么**：零 RTL 成本，直接砍 60~75% 字节数；顺带删掉 BMP 头解析和 24→16bit 转换逻辑（省 LUT）。
- **收益**：850ms → 200ms 量级；配合 P0-1 后完全无感。
- **风险**：画质靠 `bilinear.v` 放大弥补；素材要重新生成（一次性工作）。

### P1-1　修好 CMD18 多块读

- **为什么**：代码已写 90%，只差"CMD12 后等 busy 释放 + R1b 校验 + 不支持时降级"。这是"每扇区 120µs 固定开销"的唯一解药。
- **收益**：**1.7×**（1.47s → 0.85s）；配合 P0-3 后 0.28s。
- **风险**：卡兼容性；CMD12 时序错会连环失败（你已经遇到过 `fail=1`）。

### P1-2　缩小档改盒式平均 + 乘法器时复用

- **为什么**：缩小档现在是抽点（丢 3/4 能量，闪烁/摩尔纹），是**画质上最容易被评委看出来**的一处；时复用乘法器顺手把 DSP 从 23 降到 15。
- **收益**：缩小画质显著提升；DSP 79%→52%，给后续功能留空间。
- **风险**：像素流水线加 1 行延迟（`line_buf` 兜得住）。

### P1-3　统一同步复位 + `keep_hierarchy=FLATTEN` + `pack_effort=HIGH`

- **为什么**：slices 88.9% 是绑定资源，其中约 10 个百分点是**配对失败**浪费的；手册明确说 sync/async 混用会导致寄存器无法相邻摆放。
- **收益**：slices 88.9% → 82~85%，LUT −3~8%。这是"让 hold 修复不再被跳过"的前置条件。
- **风险**：异步复位的"立即生效"语义会变，必须重仿真；布局变化 → 重跑 SDRAM 读回自测。

### P2-1　字幕/字库搬进 16 块空着的 32Kb ERAM

- **为什么**：`#bram32k 0/16` 完全闲置，而字幕 512Kbit、16×16 汉字字库 512Kbit，**尺寸精确吻合**。上电从 SD 装一次（164ms）就绕开了"BRAM 不能上电初始化"。
- **收益**：每帧省 1600 字 SDRAM 读；腾 16,000 字；字幕延迟降到 ns 级；为中文 OSD 铺路。
- **风险**：ERAM 是 16 位宽，拼接要小心；`ram_style="bram_32k"` + 开输出寄存器。

### P2-2　清理 top_m2.v 的调试探针与死代码

- **为什么**：`B_DEBUG_PROBE` 宏、历史探针、`ref_top_video.v` 里的 `top`（AGENTS.md 明确"别加进任何 TD 工程"）。这些不进综合则无害，一旦宏被打开就会吃 LUT 与布线资源。
- **收益**：不确定（取决于当前是否被打开），但**这是让"资源从 88.9% 降下来"最没有副作用的一步**。
- **风险**：低（仿真回归即可）。

### 不建议做的

| 想法 | 为什么不做 |
|---|---|
| SD 4-bit 模式 | 板子只连了 4 根 SPI 线（`m2_pin.adc`），物理不可行 |
| 提升 SDRAM 带宽 / 上 APUG011 | 需要 57.6MB/s，有 500MB/s，收益 0，风险高 |
| 给 0°/180° 加 `set_clock_groups` 放松 | 你自己的 `m2.sdc` 第 64–79 行有实测反例（2048 字错 1536） |
| font_rom 改进 BRAM | 上电不能初始化；且只有 ~200 LUT，不值得 |
| 修 +576ppm 音频时钟 | 0.058% 远低于人耳阈值；改了会破坏 HDMI 音频的 N/CTS 关系 |
| retiming 全局打开 | 手册明说"尽量少用"，前后网表不可比，出问题无法定位 |

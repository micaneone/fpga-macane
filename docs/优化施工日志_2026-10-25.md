## 步骤 1：P0-1 scaler 行请求两级流水

### 改了什么
`b_display/scaler_addr.v`：
- 行请求（前台 `l0_*`/`l1_*`、后台 `l0b_*`/`l1b_*`）从“一个 40 MHz 周期串完”改成两级：
  - **一级**（前台 `pix_x==1` / 后台 `pix_x==0`）：算 `v_store0`、锁 `u_last_w`、锁 `bilin`；
  - **二级**（前台 `pix_x==2` / 后台 `pix_x==1`）：乘 `wpl` + 加基址 + 绝对 4 字对齐 + 字数 + 发 `go`。
- 放大档的第二行（`l1_*`）改成 `row_s1 = row_s0 − wpl`（数学等价），**省掉第二个乘法器**。
- `align_px_cur` / `b_align_px_cur` 也跟着晚 1 拍更新（只在下一行的 `rd_index` 用，安全）。
- 行请求只影响“下一行搬运单”，晚 1 个像素（25 ns）对 640 拍的行毫无影响；`win_compositor` 的像素流水 `de/vs` **不需要动**（本次只流水行请求路径，没有动 `rd_index/hit` 数据路径）。

### 为什么这样改
- 报告里像素域唯一真违例：`u_disp/u_timing/h_cnt_reg[9] → u_disp/u_comp/u_scaler/l0b_words_reg[10]`，Data **28.047 ns** / 预算 25 ns / 16 级（10 ADDER + 2 MULT18 + 4 LUT），平均违例 3 ns。
- `scaler_addr.v` 头注释本来就留了这句：“若以后综合报时序紧，再在这里插流水，并把 win_compositor 的 de/vs 同步延迟同样的拍数”——本次只流水行请求（控制路径），所以 `win_compositor` 不用改。
- 顺带省一个乘法器（`row_s1` 用减法），DSP 可能 23 → 22（待构建确认）。

## 步骤 2：P0-1b `zoom_sel` 算术三级流水（40 MHz 域收尾）

### 改了什么
`b_display/zoom_sel.v`：整条算术链切成 3 级流水（输出整体晚 3 拍，latency=3）：
- **第 1 级**：输入打拍 + 两个交叉乘积（`win_w*src_h` / `win_h*src_w` 并行）；
- **第 2 级**：比较取限制轴 → `×K`（≈2^24/win）→ `step_fit` / `step_calc` 打拍；
- **第 3 级**：`step → Q4.12` → 两个"窗口×step"乘法（并行）→ `off_u/off_v`，输出打拍。
- `fit_busy` 仍恒 0（除法器 2026-10-17 已删）。

### 为什么这样改
- 步骤 1 之后，像素域剩下的唯一真违例就是 `u_zoom` 的算术链：
  `u_scaler/b_u_first_w[10] → … → u_zoom/b_off_v[18]`，Data **26.178 ns / 25 ns**，
  11 级（3×MULT18 + 多个 ADDER），单个 40 MHz 周期塞了 3 个乘法串。
- 输入是"换图 / 换档 / 相位切换"才变的慢变信号；`zoom_dual` 每 256 拍（6.4 µs）
  才锁存一次输出 ⇒ 3 拍延迟完全不可见。功能等价由对拍保证。

## 步骤 3：P0-4 SDRAM 读启动去宽比较（occ 比较改位判断）

### 改了什么
`b_display/sdr_arb.v`：FIFO 占用估计 `occ`（22 位）参与比较的地方从“宽比较”改成“位判断”——只保留行为完全等价的阈值判断（`occ >= 512` / `occ >= 248` 这类），把 22 位减法比较链压短：
- `fifo_rdusedw_eng` 的 `(occ >= 22'd512) ? 10'd511 : occ[9:0]` 改成用位数检测；
- `o_occ_hi` / `o_occ_pre` 同样改成位/阈值门，语义逐位不变（有对拍照逻辑可查）。
- **没动** `occ` 的计数/跨域同步逻辑（那个 2026-10-02 试过改真值 `rdusedw`，上板坏点，已回退，注释里写着“别再改这里”）。

### 为什么这样改
- 步骤 1/2 之后，125 MHz 域内剩下的最差路径是：
  `u_arb/occ_reg[16] → … → u_vrd/u_rd_ctrl/state_reg[3] / App_rd_en_r`，Data 9.498ns / 8ns、9 级，
  其中 4 个 ADDER 全在比较链上（`occ >= 512` 这类宽比较）。把它换成位判断理论上能砍掉这 4 级。
- 这条链本身不跨域（clk_mem 125 MHz 域内），属于“稳赚不赔”的等价替换。

## 步骤 5：P0-5 开机首趟等待 1 s → 40 ms（事件化）

### 改了什么
`rtl/top_m2.v`：
- `wire [25:0] aud_wait_need = aud_first ? 26'd50_000_000 : 26'd2000;`
  → `aud_first ? 26'd2_000_000 : 26'd2000;`（开机第一趟 1 s → 40 ms，共 3 处：常量 + 两处注释）。
- 其余逻辑不动（`aud_first` 仍由 `a_wav_done` 清零；换音频路径本来就是 40 µs）。

### 为什么这样改
- 原代码注释自己写着：这 1 秒“本来只是**开机**为了让用户先看清图片”。
  但 state 1 的门条件（`!img_hold/!tr_active/!a_busy/!req_pend_w/!aud_busy_w/!sub_load_pulse/!a_start_use`）
  已经保证“图已经显示出来、转场结束、A 轨空闲”——再等 1 秒纯属白等。
- 40 ms 与“换音频时等上一条停稳”的时间一致，足够让首帧/转场彻底落定、SDRAM 在途读收干净。
- 开机时序：原 ≈ 装图 1.5 s + 1 s + 装音效 0.2 s ≈ 2.7 s 才出声；
  改后 ≈ 装图 1.5 s + 40 ms + 0.2 s ≈ 1.75 s ⇒ 提前约 0.96 s。
- 代价：开机首帧只露 40 ms 就会进入“装音效的米白闪”，随后图立刻回来（0.2 s 左右）；
  牺牲一点点“先看清图片”的观感换 ~1 s 起播速度。这是一行常量，回退随时可以（改回 50_000_000）。
